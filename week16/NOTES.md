# 16주차 배운 것 (Claude 정리) — 진단 먼저, 그리고 검색 전용 벤치

> 15주차 끝 상태: `gemma4:e4b-it-qat` + 헤딩청킹(v3) + 하이브리드 검색 + top_k 3
> 59문항 기준 51/56 (91%)

## 1. 진단부터 했다

남은 실패가 5건뿐이라 아무거나 손대면 또 순증 0이 나온다. 그래서 **5건을 먼저 열어봤다.**

| 유형 | 건수 | 내용 |
|---|---|---|
| 검색 실패 | 2 | 어휘 충돌 ("폴더", "좌우") |
| 검색 O / 생성 X | 3 | — |

**생성 실패 3건 중 2건이 같은 모양이었다.**

| 문항 | 근거 1 | 답변 |
|---|---|---|
| 춘향 적설값 열 | **현장별-비교.md** (정답 문서) | "자료에서 찾을 수 없습니다" |
| SftpCollector 쓰이나 | **미사용-코드.md** (정답 포함) | "자료에서 찾을 수 없습니다" |

**검색이 정답을 1위로 가져왔는데 모델이 포기했다.** 원인은 시스템 프롬프트였다.

```
제공된 근거에 있는 내용만으로 답하고, 근거에 없는 내용은 절대 지어내지 않는다.
근거에 질문의 답이 없으면 "자료에서 찾을 수 없습니다"라고만 답한다.
```

춘향 적설값은 `현장별-비교.md`의 **표 안에** `| 적설값 열 | ... | snowDepth | snowDepth |` 형태로 있다.
문장으로 안 쓰여 있고 표의 행·열을 짚어야 읽히는데, 모델이 "명시돼 있지 않다"고 판단했다.

**환각 방지 장치가 너무 세서 정답까지 막고 있었다.**

## 2. 프롬프트 v2 — 오늘 첫 순증

바꾼 곳은 두 줄이다.

```
- 근거의 표, 목록, 코드에서 읽어낼 수 있는 내용도 답한다. 문장으로 풀어 쓰여 있지
  않더라도 표의 행과 열을 짚어 읽으면 그것도 근거다.
- 근거를 끝까지 읽어도 답이 없을 때만 "자료에서 찾을 수 없습니다"라고 답한다.
  근거에 있는데 포기하는 것도 틀린 답이다.
```

| | 검색 | 최종 |
|---|---|---|
| v3 + 하이브리드 (프롬프트 v1) | 54/56 (96%) | 51/56 (91%) |
| **v3 + 하이브리드 + 프롬프트 v2** | 54/56 (96%) | **52/56 (93%)** |

**깨진 문항이 하나도 없었다.** 함정 3문항도 그대로 막았다. 오늘까지 손잡이 여덟 개 중
순증이 나온 건 **헤딩 청킹 / 하이브리드 / 프롬프트 v2** 셋뿐이다.

### 채점의 허점이 또 드러났다

예비 확인에서는 2건이 고쳐졌는데 총점은 +1이었다. SftpCollector 문항은 **원래부터 통과로
집계되고 있었다.** 답변이 "찾을 수 없습니다"였는데 키워드(`쓰이지 않`)가 우연히 맞았다.
**틀린 답이 맞는 답으로 세어지고 있었던 것이다.**

### 지금까지와 다른 점

| 손잡이 | 성격 |
|---|---|
| 링크 조각 제거 / 헤딩 청킹 | 인덱스 |
| top_k / 하이브리드 | 검색 |
| **프롬프트 v2** | **생성** |

생성 단계를 처음 건드렸다. 그리고 이건 **평가 세트를 59문항으로 넓혔기 때문에 보였다.**
22문항일 때는 이 유형이 1건뿐이라 원인이 안 드러났다.

## 3. 검색 전용 벤치 (`retrieval_bench.py`) — 10분을 11초로

`evaluate.py`는 59문항에 10분이 걸리는데 **대부분이 답변 생성 시간**이다.
검색만 재면 **11초**다. 반복이 50배 빨라진다.

그리고 통과/실패 대신 **정답 문서가 몇 위로 나오는지**를 본다.

| 지표 | 뜻 |
|---|---|
| Recall@k | 정답 문서가 상위 k개 안에 든 비율 |
| **MRR** | 1/순위의 평균. 1위면 1.0, 2위면 0.5, 못 찾으면 0 |

**남은 실패가 2건뿐이어도 5위→2위 같은 변화가 잡힌다.** 통과/실패로는 못 보던 해상도다.

### 기준선

| | 벡터만 | 하이브리드 |
|---|---|---|
| Recall@1 | 87.5% | 87.5% |
| Recall@3 | 92.9% | **96.4%** |
| Recall@10 | 96.4% | **100%** |
| MRR | 0.9036 | **0.9222** |
| 소요 | 12.5초 | 10.9초 |

**하이브리드가 Recall@10을 100%로 만들었다.** 정답 문서는 항상 상위 10위 안에 있다.
**못 찾는 게 아니라 순위가 낮을 뿐이다.** 남은 2건은 6위와 7위.

이건 리랭커가 정확히 겨냥하는 상황이다 — 후보 안에 답이 있는데 순서가 틀린 것.

## 4. LLM 리랭커 — 기각

후보 10개를 `gemma4:e4b`에게 주고 구조화 출력(JSON)으로 순서를 다시 매기게 했다.

| | 하이브리드 | +리랭커 |
|---|---|---|
| Recall@1 | **87.5%** | 78.6% |
| Recall@3 | 96.4% | 96.4% |
| Recall@5 | 96.4% | 98.2% |
| Recall@10 | 100% | 100% |
| **MRR** | **0.9222** | **0.8761** |
| 문항당 | **0.19초** | **19.6초** |

**100배 느려지고 정확도까지 떨어졌다.**

### 겨냥한 것만 고치고 나머지를 망쳤다

```
올라감 4건 : 6→1, 7→2, 3→1, 2→1     (목표했던 어휘 충돌 2건 포함)
내려감 8건 : 1→7, 1→4, 1→3, 1→3, 1→2 ×4
```

**내려간 8건이 전부 원래 1위였다.** 검색기가 이미 맞게 세운 것을 모델이 흔들었다.
특히 "판 모양을 위로만 정규화하면 부작용은?"이 1위에서 7위로 떨어졌다. 정답 조각이
부작용을 직접 말하지 않고 문맥으로 드러내는 형태라 작은 모델이 오판한 것으로 보인다.

### 왜 실패했나

**리랭커가 의미를 가지려면 리랭커가 검색기보다 관련도 판단을 잘해야 한다.**
유효 4.5B 모델의 판단이 `bge-m3 임베딩 + BM25` 조합보다 못했다.
범용 LLM을 관련도 판정에 쓴 것도 원인이다. 다시 한다면 전용 cross-encoder
(bge-reranker 계열)로 해야 한다.

### 이 실패를 11초 벤치가 건졌다

전체 평가(10분)로 쟀으면 시도 자체를 망설였을 것이고, 통과/실패로만 봤으면
"Recall@3 그대로, Recall@5 개선"으로 읽혀 **채택했을 수도 있다.**
MRR과 순위 변화를 봤기 때문에 "1위였던 걸 밀어냈다"가 드러났다.

## 핵심 교훈

- **고치기 전에 진단한다.** 실패 5건을 열어보니 3건이 같은 원인이었고, 그건 검색이
  아니라 생성 쪽이었다. 계속 검색만 최적화하고 있었다
- **환각 방지가 너무 세면 정답도 막는다.** "절대 지어내지 마라"의 대가가 "표에 있는 답도
  포기한다"였다
- **측정 도구를 먼저 빠르게 만들면 시도 횟수가 는다.** 10분 → 11초가 리랭커 실험을 가능하게 했다
- **통과/실패보다 순위가 해상도가 높다.** 같은 Recall@3인데 MRR은 0.9222 vs 0.8761로 갈렸다
- **리랭커는 만능이 아니다.** 검색기보다 나은 판단을 못 하면 넣는 게 손해다
- **겨냥한 것만 보면 안 된다.** 리랭커는 목표 2건을 확실히 고쳤다. 전체를 봤기 때문에 기각했다

## 현재 채택 구성

