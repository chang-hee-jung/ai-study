## 사건 1 — PATH 사건이 증명한 서버-클라이언트 구조

- 터미널에서 `hello.py`는 모델 답변을 받는데 `ollama` 명령은 "인식되지 않습니다"
- 원인: Ollama 설치 후에도 기존 터미널은 옛 PATH를 물고 있음 (프로세스는 시작 시점의 환경변수를 유지)
- **교훈: `ollama`는 클라이언트일 뿐. 진짜 일꾼은 127.0.0.1:11434의 서버.**
  12주간 짠 `chat()`은 전부 이 서버로 가는 HTTP 클라이언트였다 (mysql 클라이언트 ↔ mysqld 관계)

## 사건 3 — 콜드 로드 vs 웜 로드 (실측, qwen2.5:7b)

| | load_duration |
|---|---|
| 콜드 (모델 미탑재) | 2.56초 |
| 웜 (탑재 상태) | **0.11초 (23배 빠름)** |

- KEEP_ALIVE의 본질 = **지연 vs VRAM 점유**의 트레이드오프. 붙들면 요청당 2.5초를 벌고 4.9GB를 지불
- 실험 설계 교훈: PATH 씨름하다 측정이 늦어져 1차 관찰이 오염됨 → "끝나자마자"를 보장하려면
  명령을 한 줄로 이어 실행. **측정이 오염되면 다시 돌린다**

## 사건 4 — 13주차 감속의 물증

- qwen2.5:14b 로드 → `PROCESSOR: 38%/62% CPU/GPU` (10GB 중 ~6.2GB만 VRAM, 나머지는 RAM)
- 13주차 "4~5배 감속"을 속도로 추측만 했는데, 분할비로 처음 눈으로 확인

## 사건 5 — 8.3 tok/s 미스터리와 화면세(稅) 판결

가설: "집 PC는 RAM 2배(32GB)니 14B가 빨라질 것" → **기각**

| | 학습 PC (RAM 16GB) | 집 PC (RAM 32GB) |
|---|---|---|
| qwen2.5:14b eval rate | 10~12 tok/s | **8.2~8.3 tok/s (재현됨)** |

용의자 심문:
1. 측정 오염 → 무죄 (재측정 8.32로 재현)
2. 싱글 채널 → 무죄 (DDR5-5200 듀얼 채널)
3. 구식 CPU → 무죄 (Zen 4, 5.2GHz)
4. **GPU 분할비 → 유죄.** 7500**F** = 내장 그래픽 없음 → 모니터 출력·Chrome·VS Code·Steam 등이
   전부 4060 Ti VRAM에 세 들어 삶 (nvidia-smi: 7639/8188MiB, 모델 ~6GB 제외해도 앱들이 ~1.4GB)
   노트북은 i7-13620H 내장 그래픽이 화면을 대신 담당 → 4060의 8GB가 모델 전용이었음

## 핵심 교훈

- **용량과 대역폭은 다른 자원이다**: RAM 32GB는 "담을 수 있다"까지만. 속도는 대역폭·연산이 결정
  (디스크 4TB→8TB로 바꿔도 I/O는 안 빨라지는 것과 같음)
- **명목 스펙 ≠ 가용 용량**: "둘 다 VRAM 8GB"는 명목. 화면세를 누가 내느냐가 가용량을 갈랐다
- **스펙이 아니라 측정이 진실을 말한다**: 베이스라인(13주차에 PROCESSOR 분할 미기록)을 안 남기면
  나중에 비교할 때 대가를 치른다
- 디버깅 절차 = 인프라 그대로: 측정 → 말이 안 됨 → 용의자 목록 → 증거 수집 → 판결
