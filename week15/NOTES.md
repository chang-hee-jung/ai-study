# 15주차 배운 것 (Claude 정리) — RAG 평가 체계와 첫 최적화

> 5단계를 인프라(부하·vLLM)에서 **RAG·에이전트 심화**로 재편하고 시작한 첫 주.
> 사용자 방향: "RAG·에이전트를 공부·실습하며 최적화·고도화한 뒤 다른 곳에 적용한다"

## 왜 평가부터 만들었나

14주차에서 겪은 것 — bge-m3 언로드는 그럴듯했지만 **재보니 0%**였고,
`num_gpu`는 재봤기 때문에 27.7%를 찾았다. 그런데 `ask.py`에는 **잘 답하는지 재는 수단이 없었다.**
이 상태로 청킹이나 top-k를 바꾸면 좋아졌는지 나빠졌는지 알 수가 없다.

그래서 순서를 **평가 → 개선**으로 잡았다.

## 1단계 — 적설계 위키를 인덱스로 (`build_wiki_index.py`)

`F:\SnowViewer3D_wiki`(7/27 작업물, 문서 34개)를 재료로 썼다. 남의 문서로는 정답 세트를 못 만든다.

- 문서 34개 → **317조각** (규정 문서 10조각의 31배)
- week08 대비 추가: 폴더 재귀 탐색 / frontmatter 제거 / **조각마다 출처(source) metadata**
- 출처를 남긴 이유: 답변에 문서명을 달고, 평가에서 "정답 문서를 가져왔나"를 판정하려면 필요하다

## 2단계 — 22문항 평가 세트 (`evalset.py`)

전부 위키 본문에 답이 명시된 것만. 문항마다 `질문 / 정답 문서 / 반드시 들어갈 표기`.
함정 2개 포함 — 자료에 없는 질문(유지보수 비용), "미측정"이 정답인 질문(춘향 거리 최대값).

**두 축으로 나눠 채점한다. 섞으면 어디를 고칠지 알 수 없다.**

| 실패 유형 | 고칠 곳 |
|---|---|
| 검색 X | 청킹·임베딩·top-k |
| 검색 O + 답변 X | 프롬프트·모델·근거 조립 |

## 3단계 — 점수판이 제일 먼저 틀렸다

첫 결과는 **검색 67% / 최종 76%**였다. "검색이 낮으니 청킹을 뜯어야겠다"로 갈 뻔했다.
실제로는 **채점 결함 세 개**였다.

1. **정답 문서를 하나만 인정** — 초 오프셋(`:30`/`:54`/`:38`)은 `현장별-비교`와 `프레임-짝짓기`
   양쪽에 있는데 한쪽만 정답으로 잡았다
2. **공백에 민감한 키워드 매칭** — qwen3.5의 "5 분"을 `"5분"`과 다르다고 오답 처리
3. 키워드 채점 자체가 근사

`rescore.py`로 고쳐 재채점하니 **검색 100%, 최종 90%**. 76 → 90은 모델이 좋아진 게 아니라
채점이 정확해진 것이다. **진짜 문제는 처음부터 전부 생성 단계에 있었다.**

- 답변 원문을 json에 저장해둔 덕에 **모델을 다시 돌리지 않고 채점만 고쳐서** 재계산했다
- 숙제 1의 "말이 안 되는 숫자가 나오면 기준선을 의심하라"가 이번엔 내가 만든 채점표에 적용됐다

### 실패할 때의 거동이 점수보다 중요했다

같은 X라도 내용이 달랐다.

- **qwen2.5:14b** — 답변이 중국어로 이탈했고(시스템 프롬프트에 "한국어로만"이 있는데도),
  출처 파일명까지 중국어로 조작했다(`基础概念\帧配对.md`). 위키 문법 `[[...]]`도 새어나왔다
- **gemma4:e4b** — 한국어를 지키고, 모르면 "자료에서 찾을 수 없습니다"로 정확히 지시를 따랐다

RAG에서는 **틀린 답을 그럴듯하게 하는 모델이 제일 위험하다.**

### E4B가 2.87GB로 끝난 이유 — PLE

파일은 6.1GB인데 VRAM은 2.87GB, `100% GPU`. 나머지 3.2GB는 **레이어별 임베딩 테이블(PLE)**로
시스템 RAM에 있다. VRAM을 아낀 것이지 메모리를 안 쓴 게 아니다.

숙제 1에서 발견한 "절편이 파일보다 166 MiB 작다 → 임베딩 테이블이 VRAM 밖"이 여기서 확인됐다.
qwen은 166 MiB였고 E4B는 3.2GB로, 같은 현상의 극단이다.

**12B는 PLE 구조가 아니다.** E2B/E4B만 온디바이스용으로 그렇게 만들어졌고, GPU 밖으로 뺀 몫이
0.95GB뿐이라 VRAM을 두 배 쓰고 속도는 1/3이 됐다.

### 12B가 느린 진짜 이유

답변 51자에 47.8초. 생성은 18 tok/s니 2초면 끝난다. **45초가 근거를 읽는 데 쓰인다.**
RAG는 프롬프트에 근거를 길게 넣으므로 **생성 속도(tok/s)만 보면 안 된다.**

### qwen3 계열은 생각 모드를 꺼야 비교가 된다

`qwen3.5:9b`는 생각 모드가 기본 ON이라 160토큰을 전부 생각에 쓰고 **답변이 비어서** 나왔다.
`chat(..., think=False)`로 꺼야 공정한 비교가 된다 (`ASK_NO_THINK=1`).

## 끝내 안 풀린 Q5 — 원인은 청킹 경계

"프레임 짝짓기에서 타임라인 기준은 어떤 우선순위로 정해지나?"
**모델 4종 × 인덱스 3종 전부 실패.** 원본을 보면 답이 나온다.

```
타임라인의 기준은 우선순위대로 정해진다.      <- 문단 1 (질문과 가장 유사)

1. surface가 있으면 surface의 시각들          <- 문단 2 (실제 정답)
2. 없으면 ir의 시각들
3. 그것도 없으면 data의 시각들
```

요약 문장과 실제 목록이 빈 줄로 갈라져 있다. 문단 단위로 자르니 **질문과 가장 비슷한 건
요약 문장**이고, 검색이 그걸 1위로 가져오니 모델은 "우선순위대로 정해집니다"를 되풀이할 수밖에 없다.

**정답이 인덱스에 있는데 질문과 안 붙어 있다.** 모델을 키워도(12B도 실패) 안 풀린다.

## 채점의 한계 — 결함이 총 5건 나왔다

1. 정답 문서를 하나만 인정 2. 공백 민감("5 분") 3. "표현" vs "표시" 4. "측정되지 않았습니다"가
표기 목록에 없음 5. 키워드 채점 자체가 근사

**모두 모델이 아니라 채점표가 틀린 경우였다.** 답변 원문을 저장해둔 덕에 매번 모델 재실행 없이
재채점만 했지만, 표기 변형은 계속 새로 나온다. 제대로 하려면 **LLM 판정(judge)** 이 필요하다.

## 7단계 — LLM 판정으로 채점 교체 (`judge.py`)

키워드 채점의 표기 변형 문제를 뜻 판정으로 바꿨다. 문항마다 **정답 요지(`key`)** 를 넣고,
판정 모델에게 "기준 답안의 핵심이 답변에 담겼는가"만 묻는다. 구조화 출력(JSON 스키마)으로 형식을 강제.

**판정 모델은 `gemma4:e4b-it-qat`.** 12b는 문항당 수십 초라 176건을 못 돌린다.

### 판정기도 세 번 틀렸다 — 프롬프트가 곧 손잡이다

| 규칙 상태 | 증상 |
|---|---|
| 처음(엄격) | Q15에서 위키 원문 그대로 답했는데 "override 설명이 없다"며 오답 처리 |
| 완화 후(관대) | Q6(90초의 근거)를 부분 답변인데 정답 처리 |
| " | **qwen3.5의 "자료에서 찾을 수 없습니다"를 정답 처리** — 정답이 자료에 있는데도 |
| 다시 엄격 | 자기모순 답변("찾을 수 없습니다. 근거 2에 따르면 지리산이…")을 오답 처리 |

**세 번째가 제일 위험하다.** "모른다"를 정답으로 쳐주면 회피하는 모델일수록 점수가 올라간다.
함정 문항 규칙("모르면 정답")을 일반 문항에까지 잘못 적용한 것이다. 규칙에 못을 박았다.

> 기준 답안에 구체적인 답이 있는데 응시자가 "찾을 수 없습니다"라고 했으면 **반드시 오답**이다.
> 못 찾은 것은 실패다. 정직하게 모른다고 한 태도를 정답으로 쳐주면 안 된다.

### 판정기가 5건 중 3건 틀렸다

가장 뚜렷한 건 v2의 Q5다. 질문은 "타임라인 기준을 어떤 **우선순위**로 정하나"인데,

- v2 답변: `NearestPath로 찾음 → ±90초 이내 → 없으면 null` = **값을 짝짓는 절차.** 다른 질문에 답했다
- v3 답변: `1. surface → 2. ir → 3. data` = 정답

판정기는 v2 답변에 "우선순위"라는 **단어가 있고 번호 목록 꼴**이라 정답으로 봤다.
12B의 "빈 문자열과 0이 구분되지 않습니다"는 질문에 정확히 답했는데 이유가 없다며 오답 처리했다.

### 결론 — 키워드를 버리는 게 아니라 나란히 둔다

**LLM 판정의 값어치는 정확도가 아니라, 176건 중 사람이 볼 5건을 골라준 것이다.**
그 5건을 눈으로 보니 3건은 키워드가 맞았고 2건은 판정기가 맞았다.
어느 한쪽만 믿었으면 둘 다 틀린 결론에 도달했다.

`temperature=0`을 줬는데도 회차마다 판정이 ±1 흔들린다. **키워드는 재현되고 LLM은 안 된다.**

| | 키워드 | LLM 판정 |
|---|---|---|
| 표기 변형 | 못 따라감 | 뜻으로 판정 |
| 재현성 | 완벽 | 흔들림 |
| 경계 문항 | 기계적으로 틀림 | 애매하게 틀림 |
| 사람이 볼 양 | 22건 전부 | **불일치만** |

**실질 이득은 사람이 읽을 양이 줄어든 것이다.** 22건을 다 읽던 걸 불일치 몇 건으로 줄였다.
자기모순 답변 같은 진짜 경계 사례는 어느 채점도 대신 못 정한다.

  파일 단위로 저장은 되고 있어서 결과 json을 열어보고 진행률을 확인했다

## 8단계 — 평가 세트 확대 (22 → 59문항)

## 9단계 — 하이브리드 검색 (`hybrid.py`)

BM25 키워드 검색을 외부 패키지 없이 직접 구현해 벡터와 합쳤다.

- 한국어라 형태소 분석기가 없으므로 **띄어쓰기 토큰 + 한글 2-gram**을 함께 쓴다
  ("클래스명"이 안 잘려도 "클래", "래스", "스명"으로 걸린다)
- 두 검색을 점수로 섞지 않고 **순위로 합친다(RRF, k=60)**. 점수 정규화가 필요 없고
  한쪽이 이상한 값을 내도 덜 흔들린다
- 거리 문지기를 `dists[0]`에서 `min(dists)`로 바꿨다. 키워드로만 걸린 조각은 벡터 거리가
  없어서(9.9로 채움) 1위 거리로 막으면 통째로 차단된다

| | 검색 | 답변 | 최종 |
|---|---|---|---|
| 벡터만 | 52/56 (93%) | 52/56 | 51/56 (91%) |
| **하이브리드** | **54/56 (96%)** | 51/56 | 51/56 (91%) |

**검색은 확실히 올랐는데(93→96%) 최종은 그대로다.** 정답 문서를 2건 더 가져왔지만
근거 구성이 바뀌며 생성이 1건 깨졌다(춘향 적설값 열 — 오늘 세 번째로 흔들린 문항).

채택은 했다. 검색 96%는 실제 개선이고, 그 이득은 평가 세트 밖의 질문에서 나타난다.

## 10단계 — 남는 VRAM 5GB를 쓸 수 있는가 (결론: 못 쓴다)

채택본이 VRAM 2.87GB만 쓰고 5.1GB가 논다. 더 쓸 방법을 셋 다 재봤다.

### ① 컨텍스트 확대 — 안 늘어난다

| num_ctx | VRAM | 증가분 |
|---|---|---|
| 4,096 | 2.87GB | |
| 8,192 | 2.88GB | +4MB |
| 16,384 | 2.89GB | +8MB |
| 32,768 | 2.90GB | +16MB |

**8배 늘려도 32MB.** 14주차에 잰 qwen2.5:7b가 **토큰당 57 KiB**였는데 이건 **토큰당 1KB 남짓**이다.
온디바이스용이라 대부분의 레이어가 좁은 창만 보게 설계돼 컨텍스트를 늘려도 창고가 안 커진다.
근거를 20개 넣어도 VRAM 부담이 없다는 뜻이지만, 남는 VRAM을 여기로는 못 쓴다.

### ② 동시 처리 — 안 빨라진다

| | 시간 | 배수 | VRAM |
|---|---|---|---|
| 순차 8건 | 83.3초 | — | 2.87GB |
| 동시 2개 | 68.0초 | 1.22배 | 2.87GB |
| 동시 4개 | 65.7초 | 1.27배 | **2.87GB** |

**VRAM이 하나도 안 늘었다** = ollama가 요청을 줄 세우고 있다. 1.27배는 임베딩 호출이
생성과 겹친 것뿐이다. 병목은 메모리가 아니라 **GPU 연산**이다.

### ③ 모델 여러 개 상주 — ollama가 막는다

```
gemma4:e4b + bge-m3              -> 2개 상주 (3.49GB)   공존
          + qwen2.5:7b           -> 1개 상주 (4.42GB)   앞의 둘이 다 축출
```

합계 7.91GB로 8GB 안에 들어가는데 쫓겨났다. 가설을 세워 확인했다.

| 조합 | **파일합** | 실제 VRAM | 결과 |
|---|---|---|---|
| bge-m3 + qwen2.5:7b | 5.9GB | 5.04GB | 공존 |
| gemma4:e4b + qwen2.5:7b | **10.8GB** | **7.29GB** | **축출** |

**ollama는 실제 VRAM 점유가 아니라 파일 크기로 자리를 계산한다.**
E4B는 임베딩 3.2GB를 시스템 RAM에 두는데 그게 회계에 반영되지 않는다.

```
실제 점유   2.87GB  ->  5.1GB 남음
ollama 회계  6.1GB  ->  1.9GB 남음
```

**남는 5GB는 ollama 눈에 안 보인다.** PLE는 VRAM을 아끼는 장점이지만
스케줄러가 그걸 못 알아봐서, 다른 모델과 같이 띄울 때는 오히려 불리하다.

### 덤 — 오늘 내내 못 풀던 수수께끼가 풀렸다

평가 실행 시간이 회차마다 1.8초/문항에서 12.8초/문항까지 흔들렸다.
원인은 **e4b + bge-m3가 회계상 7.3GB로 8GB 경계에 딱 붙어 있는 것**으로 보인다.
화면이나 다른 앱이 VRAM을 조금만 더 쓰면 서로 밀어내고, 그때마다 재로딩 10초가 붙는다.
실제로 번갈아 호출하니 load_duration이 10.4초 / 6.8초 / 10.7초로 찍혔다.

**"VRAM이 남는다"와 "VRAM을 더 쓸 수 있다"는 다른 말이다.**

## 핵심 교훈

- **재는 수단부터 만든다.** 점수판 없이 하는 최적화는 좋아졌는지도 모른다
- **점수판도 검증 대상이다.** 첫 점수 76%는 채점 결함이었고, 그대로 믿었으면 멀쩡한 검색을 뜯을 뻔했다
- **답변 원문을 저장해두면 채점만 다시 할 수 있다.** 모델 재실행 없이 6개 실험을 재채점했다
- **한 문항만 보고 판단하지 않는다.** 링크 제거는 Q9를 고쳤지만 Q3를 깼다. 순증은 0이었다
- **실패의 질이 점수만큼 중요하다.** 중국어 이탈·출처 조작 vs "모른다고 답함"은 같은 X가 아니다
- **생성 속도(tok/s)는 RAG 성능이 아니다.** 근거를 읽는 비용이 지배할 수 있다
- **파일 크기 ≠ VRAM 점유.** PLE 구조는 절반 이상을 VRAM 밖에 둔다
- **채점기를 바꿔도 손잡이는 그대로다.** 판정 규칙을 조이면 회피를 잡고 정상 답을 오답 처리하고,
  풀면 그 반대가 된다. 오늘 네 번 같은 구조가 반복됐다(링크 제거 / top_k / 판정 엄격 / 판정 완화)
- **"모른다"를 정답으로 쳐주면 안 된다.** 판정기가 그렇게 굴자 회피하는 모델의 점수가 올라갔다.
  정답이 자료에 있는데 못 찾은 것은 실패다
- **구조화 출력은 공짜가 아니다.** JSON 스키마를 강제하니 문항당 1.8초가 11초로 늘었다(6배)
- **평가 세트가 좁으면 점수가 거짓말한다.** 22문항 검색 100%는 내가 읽은 6개 문서만 물어본
  결과였다. 19개 문서로 넓히니 검색 실패 7건이 드러났다. **넓히는 것 자체가 개선이다**
- **부분 지표가 올라도 최종은 안 오를 수 있다.** 하이브리드는 검색을 93→96%로 올렸지만
  생성이 1건 깨져 최종은 그대로였다. 어느 지표를 보느냐로 결론이 갈린다
- **"VRAM이 남는다"와 "VRAM을 더 쓸 수 있다"는 다른 말이다.** 남는 5GB는 컨텍스트로도,
  동시 처리로도, 모델 추가로도 못 썼다. 병목은 메모리가 아니라 GPU 연산이었다
- **스케줄러는 실제 점유가 아니라 파일 크기를 본다.** VRAM을 아끼는 구조(PLE)가
  스케줄링에서는 손해가 된다. 최적화가 다른 층에서 역효과를 내는 사례
