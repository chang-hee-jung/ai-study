# 17주차 정리

## 1단계 — 붙이기 전에 모델부터 쟀다

Hermes Agent는 도구 호출 위에 서 있는 물건이라, 붙이기 전에 우리 모델이
도구 호출을 되는지부터 확정했다. 결과가 예상보다 컸다.

### 측정 결과

4문항: 기본 호출 / 한글 인자 보존 / 도구 선택 / 과잉 호출 억제

| 모델 | 점수 | 시간 | 걸린 지점 |
|---|---|---|---|
| **gemma4:e4b-it-qat** | **4/4** | 29.5초 | 없음 |
| qwen3.5:9b | 4/4 | 36.4초 | 없음 |
| qwen2.5:7b | 3/4 | 16.7초 | `서울` → `Seoul`로 번역해서 넘김 |
| llama3.1:8b | 2/4 | 10.5초 | 경로를 `/week17/`로 뭉갬 + 불필요한 도구 호출 |
| qwen3:8b | — | — | **설치되어 있지 않음 (404)** |

### 건진 것 1 — agent.py가 지금 안 돈다

`week12/agent.py`의 `BASE_MODEL = "qwen3:8b"` 인데 이 모델이 이 PC에 없다.
13주차에 `qwen2.5 7b/14b → qwen3 8b/14b`로 세대 교체했고, 그 뒤 `qwen3.5:9b`가
들어오면서 `qwen3:8b`가 정리된 것으로 보인다. 코드는 따라가지 않았다.

**모델 이름을 코드에 상수로 박아두면 이렇게 조용히 썩는다.** 모델을 지우거나
바꿀 때 코드가 아무 말도 하지 않는다. 실행해봐야 404를 본다.

Hermes가 `config.yaml`로 모델을 빼둔 이유가 이것이다. 설정과 코드를 분리하면
모델 교체가 코드 수정이 아니라 설정 변경이 된다. 3단계에서 이 부분을 자세히 본다.

### 건진 것 2 — gemma4:e4b가 도구 호출도 1등

15주차에 문서QA로 뽑았던 그 모델이 도구 호출에서도 만점이다.
VRAM 2.87GB로 제일 가벼운데 제일 정확하다. 에이전트용 모델을 따로 둘 이유가 없어졌다.

13주차에 짰던 "손발 7B / 참모 14B" 이원화는 이제 근거가 약하다.

### 건진 것 3 — 12주차 중국어 사고와 같은 계열의 버그를 다시 봤다

`qwen2.5:7b`가 "서울"을 `Seoul`로 **번역해서** 도구에 넘겼다.
12주차에 폴더 이름을 `文档`으로 바꿔버린 그 사고와 같은 뿌리다.
모델은 인자를 "전달"하는 게 아니라 "생성"하기 때문에, 원문 보존을 지시하지
않으면 자기 판단으로 바꾼다.

`agent.py`의 SYSTEM 프롬프트에 "한 글자도 바꾸지 말고 그대로 사용한다"가 들어간
이유가 이것이다. 이번 측정은 프롬프트 없이 맨몸으로 재서 그 차이가 드러났다.

### 남는 질문

`qwen3:14b`, `qwen2.5:14b`, `gemma4:12b-it-qat`는 시간이 오래 걸려 아직 안 쟀다.
필요하면 `python week17/tool_check.py qwen3:14b` 로 개별 측정한다.

## 2단계 — 설치와 연결

설치는 `-SkipSetup`으로 붙였고, `config.yaml`에 Ollama를 openai-compatible
provider로 꽂아 바로 돌았다. 첫 응답 13초.

### 첫 실행에서 경고가 떴다

```
⚠️ Context file AGENTS.md TRUNCATED: 74668 chars exceeds limit of 31457
```

**내 예상은 틀렸다.** 나는 Ollama 기본 컨텍스트(4096)가 좁아서 터질 거라고
예고했는데, 그게 아니었다.

진짜 원인은 **실행한 폴더**였다. 설치 소스 폴더
`AppData\Local\hermes\hermes-agent` 안에서 `hermes chat`을 실행했고,
그 폴더에 `AGENTS.md`가 있었다. 열어보니 이런 파일이다.

```
# Hermes Agent - Development Guide
Instructions for AI coding assistants and developers working on the hermes-agent codebase.
```

에이전트의 시스템 프롬프트가 아니라 **그 저장소를 고치는 AI에게 주는 개발자
가이드**다. Hermes는 현재 폴더의 `AGENTS.md`를 프로젝트 컨텍스트로 자동
로드하는데, 하필 자기 소스 폴더에서 실행하니 자기 개발 문서 76KB를 통째로
집어삼킨 것이다.

다른 폴더에서 실행해보니 경고가 사라졌다. 원인 확정.

### 여기서 배운 것

**에이전트는 "지금 어느 폴더에 있는가"를 입력으로 삼는다.**

내 `agent.py`에는 그 개념이 아예 없다. 어디서 실행하든 똑같이 동작한다.
`week12/testbed`를 경로 문자열로 직접 받을 뿐이다.

Hermes는 실행 위치에서 프로젝트 파일을 읽어 그 프로젝트에 맞게 행동한다.
편리한 만큼, 오늘처럼 의도치 않은 파일을 빨아들이기도 한다. 기능이자 함정이다.

그리고 경고 문구가 좋았다. 잘렸다는 사실 + 한계값 + **해결책 3개**를 같이 줬다.
내 agent.py는 뭔가 잘못되면 그냥 에러를 뱉거나 조용히 이상하게 동작한다.

### 반전 — 내 프롬프트가 4배 크다

| | 크기 |
|---|---|
| Hermes `SOUL.md` | 513 바이트 |
| 내 `SYSTEM` 프롬프트 | **1,972 바이트** |

프레임워크가 더 거대한 프롬프트를 쓸 거라 생각했는데 반대였다.

이유는 **규칙을 어디에 두느냐**의 차이다. 내 agent.py는 "한 글자도 바꾸지
말라", "에러 나면 반복하지 말라", "보고 전에 검증하라" 같은 규칙을 전부
프롬프트에 글로 적었다. 모델이 그 글을 매번 읽고 지켜주기를 기대한다.

Hermes는 같은 것들을 **코드와 설정으로 강제한다.** 프롬프트는 정체성만
짧게 주고, 나머지는 지키지 않을 수 없게 만들어둔다.

프롬프트로 부탁한 규칙은 모델이 안 지키면 그만이다. 코드로 막은 규칙은
모델이 어길 수가 없다. 12주차에 중국어 폴더명 사고를 프롬프트 보강과
**도구 방어설계** 둘로 수습했는데, 그때 이미 이 차이를 겪었다.

### tool_loop_guardrails — 같은 발상에 독립적으로 도달했다

```yaml
tool_loop_guardrails:
  warnings_enabled: true
  hard_stop_enabled: false
  warn_after:
    exact_failure: 2
    same_tool_failure: 3
    idempotent_no_progress: 2
  hard_stop_after:
    exact_failure: 5
    same_tool_failure: 8
    idempotent_no_progress: 5
```

내 agent.py에도 있다. `MAX_ROUNDS = 8`, 그리고 같은 도구를 같은 인자로
불렀는데 또 에러나면 감지하는 `last_error_key`.

**발상이 같다.** 다만 정교함이 다르다.

- 내 것: 라운드 상한 1개 + 에러 반복 1종
- Hermes: 실패 유형 3종(완전 동일 실패 / 같은 도구 실패 / 진전 없는 반복) ×
  경고·중단 2단계

그리고 기본값이 `hard_stop_enabled: false`다. **기본은 멈추지 않고 경고만 한다.**
내 것은 8라운드에서 무조건 끊는다. 어느 쪽이 맞는지는 용도에 달렸지만,
"멈출지 말지를 설정으로 뺐다"는 게 핵심이다.

### compression — 내게 없는 것

```yaml
compression:
  enabled: true   # 자동 컨텍스트 압축
```

내 `save_memory()`는 대화 전체를 통째로 쌓는다. 오래 쓰면 `memory.json`이
계속 커지고 결국 컨텍스트 창을 넘겨 터진다. 아직 안 터진 건 오래 안 써봐서다.

Hermes는 이걸 자동 압축으로 푼다. **4단계에서 이걸 훔친다.**

### state.db — 기억을 어떻게 두느냐

내 `memory.json`은 통짜 JSON이다. 불러오려면 전부 읽고, 검색하려면 전부 훑는다.

Hermes는 SQLite에 넣고 그 위에 전문검색 인덱스를 **두 종류** 얹었다.

- `messages_fts` — 일반 FTS5
- `messages_fts_trigram` — 3글자 단위 인덱스

트라이그램을 따로 둔 이유가 있을 것이다. 한국어처럼 띄어쓰기로 단어가
깔끔하게 안 갈리는 언어나 부분 일치 검색에서 일반 FTS5는 약하다.
15주차에 BM25를 한글 2-gram으로 직접 구현했던 것과 같은 문제의식이다.

`compare.py`로 동일한 출발선을 만들고 같은 목표를 줬다.
채점은 모델의 보고가 아니라 실제 디스크 상태로 했다.

### 붙이기까지 세 번 막혔다

**첫째, Hermes는 최소 64,000 토큰 컨텍스트를 요구한다.**

그런데 첫 실행은 통과했다. Hermes가 모델에게 컨텍스트를 물어 **131,072**를
받아 캐시했기 때문이다. 그건 모델이 *할 수 있는* 최대치다.
Ollama가 *실제로 준* 것은 기본값 **4,096**이었다.

```
Hermes가 캐시한 값 : 131,072
Ollama가 준 값     :   4,096
```

검사는 통과하고 실제로는 잘렸다. 잘리는 쪽은 맨 뒤에 붙은 사용자 메시지라,
에이전트가 "지시를 주세요"라고 영어로 답했다. **양쪽 다 에러를 내지 않는다.**
각자 자기 딴엔 정상 동작이다.

`num_ctx 16384`로 정직하게 알려주니 그제야 거부했고, 그때 64K 요구사항이 드러났다.

**둘째, 64K로 올리는 방법.** 서버 환경변수 `OLLAMA_CONTEXT_LENGTH`를 바꾸면
모든 모델에 영향이 간다. 에이전트용 태그 하나만 따로 팠다(`Modelfile.agent`).

```
FROM gemma4:e4b-it-qat
PARAMETER num_ctx 65536
```

VRAM 실측 **3.15GB, CPU로 밀린 것 0GB**. 8GB 카드에 여유 있게 들어간다.
gemma4의 PLE 구조 덕에 KV 캐시가 작다.

**셋째, config.yaml에 `model:` 키가 두 번 있었다.** 24번 줄에 내장 기본값
(`anthropic/claude-opus-4.6`), 151번 줄에 내가 추가한 Ollama 블록.
YAML은 뒤에 나온 게 이기므로 내 것이 적용됐다. 조용히 덮어쓴 것이라 알아둘 만하다.

한 번 돌린 결과로 결론 내지 않는다. 15주차 judge에서 회차마다 ±1 흔들리는 것을
이미 겪었다.

**내 것이 이겼다.** 2배 이상 느리지만 세 번 다 정확히 끝냈다.

### Hermes가 진 이유 — 한글을 영어로 번역했다

실패한 두 번 모두 같은 원인이었다.

```
보고서_1분기.txt → documents
사진_야유회.jpg  → photos
```

`문서`, `사진`이라고 지시했는데 `documents`, `photos` 폴더를 만들었다.
1단계에서 qwen2.5:7b가 `서울`을 `Seoul`로 넘긴 것, 12주차에 폴더가 `文档`으로
바뀐 것과 **같은 뿌리**다. 모델은 인자를 전달하는 게 아니라 생성한다.

내 agent.py에는 이 줄이 있다.

> 폴더와 파일 이름은 사용자가 말한 한국어 이름을 한 글자도 바꾸지 말고 그대로 사용한다.

12주차 사고 뒤에 넣은 문장이다. Hermes의 `SOUL.md` 513바이트에는 그런 규칙이 없다.

3단계에서 "내 프롬프트가 Hermes보다 4배 크다"는 게 부끄러운 줄 알았는데,
**그 4배가 바로 여기서 값을 했다.** 겪어서 알게 된 것이 프롬프트에 쌓여 있었다.

일반 프레임워크는 모든 언어권을 상대하니 이런 규칙을 넣을 수 없다.
**내 도메인의 실패를 아는 것은 나뿐이다.** 프레임워크가 대신해줄 수 없는 부분이 이것이다.

### Hermes가 이긴 부분 — 도구 하나의 폭

성공한 회차의 로그다.

```
💻 $ mkdir -p .../"문서" .../"사진" .../"기타"  + 7 commands   2.7s
```

터미널 도구 하나로 셸 명령 8개를 2.7초에 끝냈다. 내 에이전트가 8라운드에
걸쳐 하는 일이다.

대신 그건 **모델에게 셸을 쥐여준다**는 뜻이다. 내가 `DANGEROUS` 집합과 승인
게이트를 만든 건 정확히 그걸 피하려던 설계였다. 속도와 안전을 맞바꾼 것이고,
어느 쪽이 옳은지는 용도에 달렸다.

### MAX_ROUNDS가 잘 가던 에이전트를 잘랐다

3회 반복 전 예비 실행에서 내 에이전트가 4/7로 끝난 적이 있다.
로그를 보니 실수를 **한 번도 안 했다.**

```
라운드 1  list_files
라운드 2~4  make_folder x 3
라운드 5~8  move_file x 4      ← 여기서 MAX_ROUNDS=8 도달
```

1 + 3 + 4 = 정확히 8. 3개 남기고 상한에 걸렸다.
검증 레이어가 "미완료"를 정확히 잡아냈지만, 이미 강제 종료된 뒤였다.

3회 반복에서는 안 걸렸다. 모델이 한 라운드에 도구를 여러 개 묶어 부른
회차가 있었기 때문이다(2라운드에 7호출, 6라운드에 11호출). **모델 기분에 달렸다.**

Hermes의 `tool_loop_guardrails`는 라운드가 아니라 **실패와 무진전**을 센다.

```yaml
warn_after:      { exact_failure: 2, same_tool_failure: 3, idempotent_no_progress: 2 }
hard_stop_after: { exact_failure: 5, same_tool_failure: 8, idempotent_no_progress: 5 }
hard_stop_enabled: false
```

진도를 내는 에이전트는 아무리 오래 걸려도 안 걸린다.
**내 상한은 건강한 진행을 벌했고, 저쪽 상한은 병적인 반복을 벌한다.**

## 4단계 — 하나 훔쳐 심기

이번 주 실험이 직접 증거를 만들어준 쪽으로 정한다.

**이식 대상: 라운드 상한을 실패·무진전 기반으로 교체**

`MAX_ROUNDS = 8` 하나로 자르는 대신,
- 같은 도구·같은 인자로 반복 실패 → 센다
